# EstateMate Raspberry Pi gate controller

A Raspberry Pi that **is** the gate. It reads a Wiegand card reader or keypad, checks the card against its own copy of the estate's credentials, pulses the door relay, and reports every decision to EstateMate. It needs no PC, no terminal and no internet connection to open the door.

It signs in as a **dedicated EstateMate device agent** and speaks the same agent protocol as the Windows, Linux, Android and ESP32 agents. That keeps it inside the project's single automatic transport (`AGENTS.md`): it is not a new device-to-Cloudflare path, and it never contacts a Hikvision terminal. The terminal record it reports for in the portal exists only to give the gate an EstateMate device ID.

This is the Raspberry Pi twin of the ESP32 sketch (`esp32-gate/EstateMateGate/EstateMateGate.ino`). The behaviour is deliberately identical — the same Wiegand decoding, the same fail-closed decisions against the same cached snapshot, the same door modes, the same event documents byte for byte, the same operations protocol and the same intervals. The differences are the ones the hardware forces: GPIO goes through the libgpiod tools instead of `digitalWrite`, the clock is the Pi's own NTP-synchronised system time, and the optional non-decision state (card cache, visitor PINs, door mode) is a file on disk instead of flash.

| File | What it is |
| --- | --- |
| `EstateMateGate.mjs` | The controller. This is the canonical source: the portal serves this file (via the generated `src/pi-gate-program.ts`), and the host tests run it. Node 22+, no dependencies. |
| `systemd/estatemate-pi-gate.service` | The service unit, identical to what `--print-service` prints. Generated by `npm run build:pi-gate`. |
| `host-test/` | A scripted fake Worker and a fake GPIO backend, so the real program is exercised end to end on any machine (`npm run test:pi-gate`). It reads the event documents from `esp32-gate/host-test/fixtures/`, so both controllers are checked against one contract. |

## Setting one up

1. **Device agent → Add agent**, and set **Runs on** to **Raspberry Pi gate controller**. Each gate gets its own agent. Never share one with a bridge: downloading the config replaces the agent's secret.
2. **Terminals & devices → Register device**: add the gate. Any model name works, for example `Raspberry Pi Wiegand controller`.
3. **Device agent → Connect terminal**: choose that terminal and the Pi agent. **Any LAN address will do, and you can leave the password empty: the Pi never dials it.** Linking is what gives the gate its EstateMate device ID. Without it, the config download contains an error explaining this, and no secret is rotated. One Pi agent serves exactly one terminal, and the portal refuses a second link.
4. On the agent row, choose **Download Pi gate program** (no secret; Managers can download it too) and **Download Pi gate config** (Administrator-only; rotates the agent secret).
5. Put both files on the Pi — `/opt/estatemate/pi-gate/EstateMateGate.mjs` and `/etc/estatemate/pi-gate.json` are the paths the unit expects — and check the wiring with:

   ```bash
   sudo node /opt/estatemate/pi-gate/EstateMateGate.mjs --check
   ```

6. Install the service, which starts the gate now and on every boot:

   ```bash
   sudo node /opt/estatemate/pi-gate/EstateMateGate.mjs --install-service
   ```

   or copy `systemd/estatemate-pi-gate.service` to `/etc/systemd/system/` and run `sudo systemctl enable --now estatemate-pi-gate`. The agent shows **online** within a minute; `journalctl -u estatemate-pi-gate -f` shows every card the reader presents.

`estatemate-gate.json` contains the agent secret. Keep it on the Pi, readable by root only (0600), and out of Git and shared drives. Downloading the config again rotates the secret, and a Pi still running the old file stops being accepted. The program file holds no secret at all, so re-downloading it after an update changes nothing.

## Wiring (defaults; override any of them in the config file)

| Signal | GPIO (BCM) | Notes |
| --- | --- | --- |
| Wiegand D0 / D1 | 17 / 18 | **Level shifting needed.** Most readers drive the data lines at 5 V; the Pi's GPIO are 3.3 V and are not 5 V tolerant. Use a 74AHCT125/74LVC245 level shifter, or a divider (1 kΩ in series, 2 kΩ to ground) per line. The lines idle high, so the config enables the internal pull-ups. |
| Door relay | 25 | Active HIGH (`relayActiveHigh`). Pulsed for `doorOpenMs` (3000 ms). Never drive the relay coil from a GPIO: use a relay board (or a transistor and a flyback diode) with its own 5 V supply and a **common ground**. |
| Exit button | 27 → GND | Internal pull-up (`exitButtonPullUp`). `null` disables it. A normally-open push button is all that is needed. |
| Reader LED / beeper | off | `readerLed` / `readerBuzzer` (BCM numbers), active low by default (`readerActiveHigh: false`). |

Defaults: chip `gpiochip0`, D0 17, D1 18, relay 25, exit 27. Only the numbers belong in the config; everything else has a default. The relay line is held by the program itself (through `gpioset`), which is why the stock unit runs as root — a dedicated user works too, with `SupplementaryGroups=gpio` and access to `/dev/gpiochip0`.

GPIO is driven through the `gpiod` command-line tools (`gpiomon` / `gpioset`), which are present in Raspberry Pi OS. Both libgpiod generations are supported: the version is probed at startup, and a notice is printed when v1 cannot set the exit button's pull-up.

Supported Wiegand frames: 26- and 34-bit cards with parity checking, other lengths from 26 to 64 bits read as raw data, and 4-bit or 8-bit keypad bursts (`*` clears, `#` submits). The decimal number the reader produces is the card number. Leading zeroes are ignored when matching, so a reader's `1234` matches a card stored as `0000001234`. Point a card at the reader and read the log to compare it with the portal.

## How it decides

- **Cards** are checked against a local snapshot of the estate's active cards from `credential-snapshot`. The first refresh downloads the full snapshot, page by page, and swaps it in only after the last page arrives; later refreshes are deltas, sent every 2 minutes and whenever a card operation arrives. Removals take revoked cards out. The snapshot is saved to disk, so after a restart the gate works straight away, even offline.
  - A controller that has never loaded a snapshot denies every card (`cache_not_ready`). That is the right failure: no snapshot, no estate.
  - A failed refresh keeps the previous snapshot, page for page, and the failure is visible in the heartbeat as `lastSyncError`.
  - Cards with an expiry need a set clock. A Pi without NTP is denied with `clock_not_set` for those cards; the portal's `serverTime` is adopted while the local clock is unusable, exactly as the sketch does.
  - Capacity defaults to 100,000 cards. A full snapshot larger than that is refused with an explicit error in the heartbeat rather than loaded partially.
- **Visitor PINs** arrive as the normal `upsert_visitor` / `revoke_visitor` operations and are stored on the Pi. A PIN opens the door only inside its validity window. The typed PIN never leaves the controller: events name the visitor's employee number only. Five wrong PINs within a minute lock the keypad for a minute (`too_many_attempts`). Visit counts stay an EstateMate-side rule, as they are for terminals.
- **Portal door commands** (Remote door control) are carried out on the relay: momentary open, close, remain open, remain closed and resume. The door mode survives a restart. *Remain closed* refuses cards and PINs.
- **The exit button always opens the door, in every mode**, for life safety.
- **Person and fingerprint work** is not advertised in the heartbeat, so the Worker never routes it here. Anything unexpected is answered with a clear failure, never silently dropped.

## What the portal sees

- **Heartbeat** (every 60 s): the terminal is reported as `stream: up` (the controller *is* the gate), and the snapshot health and last decision use the same `remoteVerify` shape the Remote Network Verification panel reads.
- **Events**: each card, PIN and exit-button event is sent as an `AccessControllerEvent` document with the controller's verdict attached (`remoteVerification.decision/reason/doorResult`). Up to 64 events are buffered while offline; the newest are kept and dropped ones are counted.

## Command line

```bash
node EstateMateGate.mjs --config /etc/estatemate/pi-gate.json   # run the gate (what the unit does)
node EstateMateGate.mjs --check                                # validate the config and open the GPIO lines, then exit
node EstateMateGate.mjs --once                                 # one heartbeat, snapshot, operations poll and event flush
node EstateMateGate.mjs --print-service                        # print the systemd unit for this installation
sudo node EstateMateGate.mjs --install-service                 # install, enable and start it
```

`ESTATEMATE_PI_GATE_CONFIG` and `ESTATEMATE_PI_GATE_LOG_LEVEL` override `--config` and `--log-level`.

## Testing and changing it

Edit `EstateMateGate.mjs`, then run:

```bash
npm run build:pi-gate      # regenerates src/pi-gate-program.ts and the systemd unit
npm run test:pi-gate       # the host tests: real program, fake Worker, fake GPIO
npx vitest run test/raspberry-pi.test.ts
```

The host test drives the real program with a scripted reader (`gpio.backend: "fake"`), a stub Worker and no hardware: Wiegand decoding, the fail-closed snapshot rules, the door modes, the PIN lockout, the operations protocol, persistence across a restart, and the event documents — which it compares byte for byte with the ESP32 host test's fixtures. A final check spawns the program as a child process and watches it sync, decide and report exactly as it would on a Pi.

`test/raspberry-pi.test.ts` fails if `src/pi-gate-program.ts` or the systemd unit drifts from `EstateMateGate.mjs`. If you change the event document, update `esp32-gate/host-test/fixtures/` as well; both controllers are checked against those files.

**Not verified on hardware in this repository.** The program is exercised on the host with GPIO mocked. Real wiring — level shifting, the relay board's ground, the exit button — has to be checked on a bench Pi with a reader and a relay before a gate is trusted to it.
